# Evaluation runs

Measures whether the UI Kit's rules, context and checks improve agent-written
UI, and at what cost. Re-run everything with one command:

```bash
node evals/run.ts all            # prepare, render mocks, run the plan, review, report
```

or step by step: `prepare`, `mocks`, `run`, `review`, `report` (see `run.ts`).
`run` and `review` skip work that already has results, so an interrupted plan
resumes where it stopped; `--force` re-runs. Needs Node ≥ 22.18, Chromium
(Playwright), git and an authenticated Claude Code CLI (`claude`).

Installs, runs and reviews happen in a work area outside the repo
(`$TMPDIR/uikit-evals`, or `UIKIT_EVALS_WORK`), so an agent can never walk up
into this checkout's CLAUDE.md, AGENTS.md or rules. Results come back to
`results/`.

## What a run is

One scenario × setup × model × repetition:

1. **Clean app.** A fresh copy of `template/` (the UI Kit CLI's Vite app, fixed
   once: icon set installed, layout outside `pages/`, every check passing) in a
   folder with a random name, with its own copy of an install of this
   checkout's UI Kit (`prepare` builds and packs it; third-party versions are
   pinned by `template/package.json` and the base lockfile). Scenario files (a
   mock API) and mock PNGs are copied in, then the folder is made a git repo
   with the starting state (and setup) committed: the agent's work is its diff.
2. **Setup** (`lib/setups.ts`), the only thing that varies between setups:

   | Setup                    | Guide (AGENTS.md / CLAUDE.md) | Lookups                       | Gate |
   | ------------------------ | ----------------------------- | ----------------------------- | ---- |
   | `baseline`               | –                             | –                             | –    |
   | `context`                | ✓                             | CLI, named by the guide       | –    |
   | `checks`                 | –                             | –                             | ✓    |
   | `both`                   | ✓                             | CLI                           | ✓    |
   | `guide-mcp` (delivery)   | ✓                             | CLI + MCP server              | –    |
   | `guide-skill` (delivery) | ✓                             | CLI + `build-list-page` skill | –    |

   The gate is `uikit-tools check --gate` as a Claude Code Stop hook: when the
   agent tries to finish with violations, they go back to it, up to 3 rounds.

   Where the setups overlap, by design (they are what a team would ship):
   - the guide names `uikit-tools check`, so a `context` agent may run the
     checks itself. That is part of "context"; the report counts it
     (self-check) so its effect can be told apart from the gate's.
   - each gate message carries the rule's fix and names `uikit-tools rule <id>`,
     so a `checks` agent gets some rule text, but only for rules it broke.
   - the lookups CLI is installed in every setup (it ships with the UI Kit);
     without the guide, nothing tells the agent it exists. The report counts
     lookups per run.

3. **Agent.** Headless Claude Code (`claude -p`) with the ticket as the prompt,
   a pinned model ID (`lib/paths.ts`), a fresh session, project settings only
   (no user memory, no other MCP servers), permissions bypassed, and no web,
   sub-agents or publishing. Its transcript (`agent.jsonl`) gives cost, turns
   and which UI Kit tools it used (CLI lookups, MCP calls, skill, self-checks).
4. **Scoring, after the agent finishes and never shown to it:**
   `uikit-tools check --report` (violations by rule and the choice made per
   rule), type check, build, and screenshots of the scenario's screens.
5. **Blind review** (`review`): a separate model scores 0–2 what checks
   cannot — data states, status colours, visual layout — from the screenshots,
   the agent's code (comments stripped) and the ticket only, in a folder with
   a random name.
6. **Validity.** A run is invalid, listed in the report and left out of every
   mean, when the agent failed or timed out, the check could not report, the
   agent changed no UI file, or a gated setup's gate did not run or errored.

## The plan

6 scenarios (`scenarios/README.md`) × 4 setups × 2 models (Sonnet, Haiku) × 3
runs, plus the CRUD scenario × 2 delivery setups × 2 models × 3. "Guide only"
in the delivery comparison is the `context` setup's CRUD runs.

## Outputs

- `results/<run>/` (not committed): `result.json`, `check.json`, `gate.json`,
  `review.json`, `agent.jsonl` (stream-json transcript), the files the agent
  changed, `screens/*.png`. `results/manifest.json`: UI Kit commit and package
  versions, Claude Code version, model IDs and reviewer.
- `reports/runs.json` (committed): one compact record per run.
- `reports/report.md` (committed): the tables, regenerated by `report`.
- `reports/FINDINGS.md`: what the numbers say, written by hand.

## Known limits

- n = 3 per cell: differences of one violation per run are noise.
- Checks are file-scoped and lexical (see `packages/tools/README.md`); the
  review covers what they cannot see, but one reviewer model is one opinion.
- One agent host (Claude Code). Other hosts are out of scope.
- The template's API is an Orval-style client over fixed mock data, not the
  live AssetEvent API Bruno's spike used.
